What the SC//HyperCore REST API actually does — not what the spec says.

Field-tested notes for writing code against the SC//HyperCore REST API. The conventions here differ from what you'd guess from a typical REST API; getting them wrong produces misleading 400s, silent no-ops, and race-condition 500s.

Verified on SC//HyperCore 9.6.x & 9.7.x https://<node-ip>/rest/v1/ Live spec: /rest/v1/openapi.json
These notes describe observed behavior, including quirks the official spec doesn't capture. When the spec and these notes disagree, the notes reflect what the server actually enforces on the versions listed. SC//HyperCore is the product name — older material may say “HC3”, which is obsolete.

The six rules that prevent 90% of bugs

Internalize these before writing a single call. Most confusing SC//HyperCore failures trace back to skipping one of them.

1

Wait for the task after every mutating call

Every POST / PATCH / DELETE can return a taskTag. Poll GET /TaskTag/<tag> until terminal before the next call. A mutating call with no task-wait is always a bug — skipping it causes intermittent 500s when a second call lands mid-flight.

2

Every GET returns a single-element array

Even GET /VirDomain/{uuid} and GET /TaskTag/{tag} return [ {…} ], not a bare object. Unmarshal into a list and take element 0. Typed clients that decode into a struct fail with “cannot unmarshal array”.

3

Fetch-then-filter

Query filters like ?virDomainUUID=… are rejected with 400 on many endpoints (snapshots, schedules, block/net devices). Fetch the full collection and filter client-side — or read the embedded blockDevs/netDevs arrays.

4

Self-signed TLS

Clusters ship self-signed certs. For labs, verify=False / -k (with a comment). For production, pin the node certificate as the CA bundle rather than disabling verification.

5

Check for an in-progress update first

While SC//HyperCore software self-updates, the API is effectively read-only. Before a batch of writes, check GET /update/update_status.json (no auth, not under /rest/v1/) — idle when updateStage is COMPLETE or empty.

6

There is no cluster VIP

Every endpoint is a specific node's IP. If that node dies, the endpoint is dead even though the cluster is fine. Discover all nodes via GET /Node (lanIP) and fail over client-side.

# Rule 1 — the task-tag wait every mutating call needs
resp = session.post(url, json=payload)
tag = resp.json().get("taskTag")
if tag:
    while True:
        task = session.get(f"{base}/rest/v1/TaskTag/{tag}").json()[0]
        if task["state"] not in ("RUNNING", "QUEUED"):
            break
        time.sleep(1)
    if task["state"] in ("ERROR", "UNINITIALIZED"):
        raise RuntimeError(task.get("formattedMessage", "task failed"))
# COMPLETE = success; ERROR / UNINITIALIZED = failure; any other non-running = success

Detecting versions & capabilitiesGET /Cluster
  • Platform version: GET /Cluster → icosVersion (e.g. 9.6.27.225000, 9.7.4.225310). This is the value to gate features on.
  • v2 API presence: any /rest/v2/ GET returns 404 on 9.6, normal responses on 9.7.1+. Live v2 spec: /rest/v2/openAPI.json (capital “A”).
Don't capability-detect from the v1 spec's version string. 9.6.27 and 9.7.4 both report spec version 1.3.2 while their contents differ (the labels schema exists only in the 9.7 spec). Check icosVersion, or fetch the spec and look for the specific path/schema — never the spec version number.

Features that genuinely require 9.7.1+ (v2-only or introduced alongside it): useUEFISecureBoot (create-time, v2), labels & runnable on VirDomain/VirDomainBlockDevice, /SNMPConfig, /VirDomainReplication, attemptQuiesce on snapshot create, and /VirtualDisk/upload returning a taskTag that covers conversion (the v1 upload also returns a taskTag, but it doesn't cover the conversion phase). Not in that list: snapDiff (CBT) — a v1 endpoint available on 9.6 too.

AuthBasic · session
  1. HTTP Basic on every request — simplest for scripts, and what most examples use.
  2. Session cookie — POST /login with {"username":…,"password":…,"useOIDC":false} returns a sessionID (JSON + cookie). Pass Cookie: sessionID=<id> afterward, and POST /logout when done so sessions don't linger.
curl -sk -u <user>:<pass> https://<node-ip>/rest/v1/Cluster | python3 -m json.tool
Tip Create a dedicated, least-privilege API user per integration rather than sharing an admin account — you get a clean audit trail, and revoking one integration doesn't disturb the others.

Cluster & nodes/Cluster · /Node

GET /Cluster returns a list (usually one). Fields of note: clusterName (not name), icosVersion, uuid.

PATCH /Cluster/{uuid}   {"clusterName": "new-name"}   ✓ correct
PATCH /Cluster/{uuid}   {"name": "new-name"}          ✗ 400 "Property not allowed"

GET /Node is read-only (no POST/PATCH/DELETE). disposition cannot be set via REST. lanIP is the per-node API address — the basis for the failover in rule 6.

Virtual machines/VirDomain

GET /VirDomain returns the full VM list with embedded blockDevs (disks) and netDevs (NICs). Use those embedded arrays rather than querying the BlockDevice/NetDevice endpoints with a filter (rejected — rule 3).

Power actions — POST /VirDomain/action

Body is a list:

[{"virDomainUUID": "<uuid>", "actionType": "START"}]

Valid actionType: START, SHUTDOWN, STOP, PAUSE, REBOOT, RESET, LIVEMIGRATE, NMI.

  • SHUTDOWN sends an ACPI signal the guest may ignore. Poll state until SHUTOFF/SHUTDOWN, with a hard-STOP fallback on timeout.
  • STOP is an immediate hard power-off (UI “Power Off”). FORCE_STOP is not valid.

Live migration

POST /VirDomain/action
[{"virDomainUUID": "<uuid>", "actionType": "LIVEMIGRATE", "nodeUUID": "<target-node-uuid>"}]
  • "LIVEMIGRATE" has no underscore — "LIVE_MIGRATE" returns 400.
  • Target field is nodeUUID, not targetNodeUUID.
  • POST /VirDomain/migrate exists in the spec but returns 500 on 9.7.x — don't use it.

Clone — POST /VirDomain/{uuid}/clone

{"template": {"name": "clone-name", "description": "..."}}
  • Carried from source (unless overridden in template.*): description, tags, machine type, vCPU/memory, disks (new disk UUIDs), NICs, SMBIOS.
  • Always reset by design (9.7.x): labels → {} and runnable → true on every clone path. Supports the gold-master template workflow. Re-apply with a post-clone PATCH.
  • MAC addresses are regenerated by default. To keep them (UI “Clone Existing MAC Addresses”), pass the source's netDevs — including macAddress — in template.netDevs. Only when the source is retired/off; duplicate live MACs break the network.
  • Do not pass template.smbios — it silently drops both the override and the source's SMBIOS. Clone without it, then PATCH.
  • bootDevices on clones of cloud-image VMs can come out empty — set it explicitly post-clone.

useUEFISecureBoot v2 · 9.7.1+ — create-only

The field doesn't exist in v1 at all (absent from the v1 spec and v1 GET /VirDomain on every version). On 9.6 there is no way to read or set it via REST. On 9.7.1+ via /rest/v2/VirDomain:

  • Readable on GET, settable at create time only via options.useUEFISecureBoot.
  • PATCHing it, or passing it as a clone override, is a silent no-op (200, task COMPLETE, value unchanged). The v2 spec doesn't mark it read-only — don't trust that.
  • Defaults to true, even on BIOS VMs where it's meaningless.
Consequence If a VM needs Secure Boot off (a migrated Windows VM not enrolled, or a Linux guest with an unsigned kernel), set it in the v2 create call — you cannot flip it to false afterward through the API.

Disk create — POST /VirDomainBlockDevice

{"virDomainUUID": "<uuid>", "type": "VIRTIO_DISK", "capacity": 10737418240, "cacheMode": "NONE"}
  • type: IDE_DISK, SCSI_DISK, VIRTIO_DISK, IDE_CDROM, IDE_FLOPPY, NVRAM, VTPM.
  • cacheMode: NONE, WRITEBACK, WRITETHROUGH.
  • description is rejected on POST. Hot-add / hot-remove against running VMs works.
  • tieringPriorityFactor (int, default 8): SSD-tiering priority. 0 bypasses SSD tiering — useful for scratch/migration-staging disks. On tiered clusters, all SSD tiers must be below 90% full for snapshots/clones/creation (a CRITICAL condition fires otherwise). No effect on all-flash — safe to set unconditionally. Restore the default (8) on any disk that becomes a production disk.

NIC create — POST /VirDomainNetDevice

{"virDomainUUID": "<uuid>", "type": "VIRTIO", "vlan": 0, "connected": true}

type: RTL8139, INTEL_E1000, VIRTIO, PCNET.

Labels9.7+ · base64

On VirDomain and VirDomainBlockDevice, 9.7+ only. Absent from the 9.6 spec and responses. On 9.7.x it works through both v1 and v2 — though some 9.7 builds' v1 spec omits the schema even while the server enforces it.

Not a flat map labels is a map of objects with a single value field, and the value must be base64-encoded.
"labels": {
  "env":   {"value": "cHJvZHVjdGlvbg=="},
  "owner": {"value": "b3BzLXRlYW0="}
}

Snapshots & schedules/VirDomainSnapshot

Listing

GET /VirDomainSnapshot rejects ?virDomainUUID= (rule 3). Fetch all and filter on snap["domainUUID"] — the field is domainUUID, not virDomainUUID.

Create

POST /VirDomainSnapshot
{"domainUUID": "<vm-uuid>", "label": "my-snapshot", "type": "USER", "replication": false}
  • Field is domainUUID — virDomainUUID returns 400.
  • type: "USER" for caller-initiated snapshots.
  • SC//HyperCore software defaults replication to true — override to false for transient snapshots, else it's pushed to any replication target (wasted bandwidth, delayed local deletion).
  • labels rejected on POST and PATCH (PATCH = 405). Use the single-string label field.

Response shape gotchas

No top-level blockDevices Per-disk metadata captured at snapshot time (type, capacity, cacheMode) lives under domain.blockDevs — the embedded copy of the VM as it was. A decoder looking for a top-level disk array silently gets nothing.
  • deviceSnapshots is storage-level only — disk UUIDs, serial numbers, checksums. No type/capacity/cacheMode; don't use it as disk metadata for restores.
  • labels appears but is always empty (write-rejected).

Clone a disk from a snapshot shape varies by build

The accepted body for POST /VirDomainBlockDevice/{live-disk-uuid}/clone varies between builds. On 9.7.3 the server enforces:

{
  "options":  {"regenerateDiskID": false},
  "snapUUID": "<vm-snapshot-uuid>",
  "template": {
    "virDomainUUID": "<target-vm-uuid>",
    "type": "VIRTIO_DISK",
    "capacity": 10737418240,
    "cacheMode": "NONE"
  }
}
  • UUID in the path = the live disk's UUID (matches deviceSnapshots[].uuid); snapUUID in the body = the VM snapshot's own UUID (not a per-device UUID).
  • template.type and template.capacity are required. The clone auto-attaches to template.virDomainUUID.
  • template.name is silently dropped (arrives as name: ""). PATCH post-clone — works on 9.7+, silently ignored on 9.6.
  • Snapshot data is independent of the live disk: deleting the live device doesn't invalidate the snapshot.
  • DELETE /VirDomainBlockDevice also strips that disk's UUID from VirDomain.bootDevices — capture boot order before detaching anything you'll reattach.
regenerateDiskID Defaults to true on attach/clone, which regenerates the GPT UUID / MBR signature and breaks bootable images (GRUB stores the disk UUID; Windows stores the MBR signature in BCD). Always send "regenerateDiskID": false unless you specifically need a new disk identity.

Snapshot schedules

Endpoint is VirDomainSnapshotSchedule (not SnapshotSchedule). Rejects ?virDomainUUID= — fetch all, filter client-side.

Cluster settingsDNS · time · SMTP · users

DNS — /DNSConfig

Fields: serverIPs (list), searchDomains (list).

Time

  • NTP servers: GET/POST/DELETE /TimeSource, field host. To replace the set: DELETE each existing entry (each returns a task tag — wait!), then POST new ones.
  • Timezone: GET/POST/PATCH /TimeZone, field timeZone (e.g. America/Chicago). PATCH returns a task tag — wait before further time calls.

Alert targets

  • Email — /AlertEmailTarget: emailAddress, resendDelay (s), silentPeriod (s).
  • Syslog — /AlertSyslogTarget: protocol needs the full prefix "SYSLOG_PROTOCOL_UDP" / "SYSLOG_PROTOCOL_TCP". Bare "UDP" = 400.

OIDC — /OIDCConfig

Fields: clientID, configurationURL, scopes, sharedSecret, certificate.

Write-only sharedSecret — GET always returns "", but POST/PATCH requires at least one of sharedSecret or certificate non-empty. You can't round-trip the secret through the API; store a placeholder and warn on restore.

Users & roles

GET/POST/PATCH/DELETE /User — username, password, fullName, roleUUIDs (list), sessionLimit, sessionExpiration. GET /Role is a read-only list. GET /Registration is read-only.

TLS certificate managementPOST /Certificate

POST /Certificate with {"certificate": "<PEM>", "privateKey": "<PEM>"} (field is privateKey, camelCase).

  • Per-node, not cluster-wide. One POST updates only the node you connected to. Re-certificate a whole cluster by POSTing to every node's IP (GET /Node → lanIP).
  • The upload restarts that node's API server — the HTTPS connection drops mid-call. Wrap the task-tag wait in a retry loop tolerating connection-reset / SSL-EOF for several attempts; the upload usually succeeded.
  • Validate before uploading — a mismatched key or expired cert can leave the API unreachable (console-only recovery). Check key↔cert match, expiry, and SAN coverage.
  • SAN tips: include every node FQDN and every node IP; IPs must be IP: SAN entries (a DNS:10.0.0.1 entry never matches).
  • No GET on /Certificate and no factory reset. To inspect, open a TLS connection and read the presented cert. To return to self-signed, upload a fresh self-signed cert (with a correct SAN).
ISO images/ISO

ISOs use /ISO — /VirtualDisk/upload rejects .iso (“File type is invalid”).

Upload — three steps, each task-tag-waited

1. POST /ISO             {"name": "file.iso", "size": <bytes>, "readyForInsert": false}
   → {"taskTag": ..., "createdUUID": "<uuid>"}
2. PUT  /ISO/{uuid}/data  Content-Type: application/octet-stream, Content-Length: <bytes>, raw body
3. PATCH /ISO/{uuid}      {"readyForInsert": true}

name must end in .iso; size is create-only; the read-only path field is what you mount.

Mount / insert / eject

POST /VirDomainBlockDevice
{"virDomainUUID": "<vm-uuid>", "type": "IDE_CDROM", "capacity": 0, "cacheMode": "NONE", "path": "<iso.path>"}

To swap media on a running VM, PATCH the CDROM with both path and name: {"path": "<iso.path>", "name": "<iso-name>"} to insert, {"path": "", "name": ""} to eject. Sending only path fails the task. No ISO download endpoint (GET /ISO/{uuid}/data → 405).

Virtual disks (non-ISO images)/VirtualDisk/upload

.vmdk, .qcow2, .vhd/.vhdx, .img use the VirtualDisk endpoint.

PUT /rest/v1/VirtualDisk/upload?filename=name.ext&filesize=N
Content-Type: application/octet-stream
Content-Length: N
<raw bytes>
  • The filename extension determines the format and is required.
  • Content-Length is required — chunked transfer encoding is rejected. Streaming from a URL? Get the size from a HEAD request first.
  • Returns {"taskTag": …, "createdUUID": …} — wait for the task.
Conversion tracking SC//HyperCore software renames the disk during processing: uploading-<name> → converting-<name> → <name>. The record has no state field — poll name until it equals the final name. (ISOs have no converting phase; the v2 API returns a taskTag covering conversion.)
# Stream a disk image from a URL to the cluster without a temp file
URL="https://example.com/disk.img"
FILESIZE=$(curl -sI "$URL" | awk 'tolower($1) ~ /content-length/ {print $2}' | tr -d '\r')
curl -L "$URL" | curl -u <user>:<pass> -k \
  -H "Content-Type: application/octet-stream" \
  -H "Content-Length: $FILESIZE" \
  -T - "https://<node-ip>/rest/v1/VirtualDisk/upload?filename=disk.img&filesize=$FILESIZE"
Conditions (health alerts)GET /Condition

GET /Condition — the value field is a JSON boolean. Useful pattern on API errors during heavy operations (imports, clones): fetch /Condition and surface any SET CRITICAL/ERROR conditions alongside the HTTP error — “SSD tier full” explains a 400 far better than “Bad Request”.

Cloud-image VM gotchasUbuntu cloud images

VMs from cloud images (clone + cloud-init cloudInitData) have two independent failure modes that both surface when a second disk is attached and the VM reboots:

  1. Empty bootDevices → BIOS reports “No bootable device”. Always set bootDevices explicitly (PATCH the VM with the OS disk's UUID) after cloning/creating.
  2. Grub uses root=/dev/vda1 because Ubuntu cloud images set GRUB_DISABLE_LINUX_UUID=true — after a second disk shifts device ordering, the initramfs hangs. Fix inside the guest (re-enable UUID-based root) or keep disk ordering stable.
Baseline Install qemu-guest-agent — without it, GET /VirDomain/{uuid} shows guestAgentState: UNAVAILABLE and ipv4Addresses: [], so you can't find the VM's IP via the API.
"cloudInitData": {"userData": "<base64>", "metaData": "<base64>"}
Changed Block Tracking (snapDiff)v1 · 9.6 & 9.7

POST /rest/v1/VirDomainBlockDevice/{disk-uuid}/snapDiff with {"snapshotSerialFrom": N, "snapshotSerialTo": M} returns an array of changed block intervals ([{"lower": …, "upper": …}, …]) between two snapshot serials — the native CBT API used by backup integrations.

Available in the v1 API on both 9.6 and 9.7 (present in both versions' v1 specs and the v2 spec).

  • Serials come from VirDomainSnapshot.deviceSnapshots[].serialNumber (different from snapshot UUIDs).
  • snapshotSerialFrom: 0 means HEAD (live device state).
  • Although a POST, the operation is read-only — no taskTag, no task wait needed.
SC//Fleet Manager™ APIapi.scalecomputing.com

SC//Fleet Manager™ has its own API, separate from that of SC//HyperCore software: https://api.scalecomputing.com/api/v2 with an api-key header (generate keys at fleet.scalecomputing.com). Standard public TLS — no self-signed concerns. Collection endpoints are paginated (offset/limit, max 200 per page) — iterate if you have more clusters than one page.
